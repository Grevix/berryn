# Berryn 0.1.0 Risk Register & Hostile Architectural Review
## Comprehensive Risk Assessment & Technical Sanity Analysis

---

## 1. Executive Summary

This document presents a **hostile architectural review** of the Berryn 0.1.0 Umbrella Implementation Blueprint. The goal is challenging architectural assumptions, identifying failure vectors, evaluating silent data loss paths, and providing actionable mitigations before launching codebase construction.

---

## 2. Hostile Architectural Review: 20 Core Questions & Answers

### Q1: Can this blueprint actually be implemented by an engineering team?
**Answer**: Yes. The package breakdown (`@berryn/core`, `@berryn/security`, `@berryn/project-inspect`, `@berryn/xlsx-*`, `@berryn/codemod`) isolates scope cleanly. By structuring historical roadmap versions into internal phases (`0.1.0-P0` to `0.1.0-P11`), implementation proceeds incrementally without circular blocks.

### Q2: Is pulling historical 0.2.0–0.5.0 capabilities into 0.1.0 too broad?
**Answer**: It is ambitious, but architecturally sound if phase ordering is enforced strictly. Building AST codemods (`P2`), semantic validation (`P3`), compatibility facade (`P4`), and CI automation (`P5`) under the `0.1.0` umbrella delivers a complete migration infrastructure tool from day one rather than a incomplete prototype.

### Q3: Does pulling 0.2.0–0.5.0 capabilities forward introduce architectural technical debt?
**Answer**: Only if temporary hacks or regex shortcuts are permitted. The plan explicitly forbids regex code replacements, mandates `ts-morph` AST nodes, enforces vertical-neutral core types, and mandates zero silent data loss.

### Q4: Are package boundaries still coherent under the umbrella model?
**Answer**: Yes. `@berryn/core` owns vertical-neutral run context; `@berryn/security` owns limits and path sandbox; `@berryn/xlsx-inspect` owns ZIP/OPC reading; `@berryn/codemod` owns AST code transforms. Package dependencies flow strictly downward.

### Q5: Are security controls present from day one or deferred to later phases?
**Answer**: Security controls (`@berryn/security`) are introduced in **Phase 0** (`0.1.0-P0`) before any archive parser or XML processing logic is written. All ZIP and XML operations pass through resource budget guards.

### Q6: How are unsupported or unknown XLSX features handled without silent corruption?
**Answer**: OOXML parts that are not modeled semantically (e.g., custom XML, legacy VML) are tracked in an OPC Preservation Manifest. During workbook transformation, unmodeled parts are preserved opaquely byte-for-byte. If opaque preservation is impossible, Berryn halts and emits `BRN-XLSX-MUTATION-REJECTED`.

### Q7: Can the codemod engine be reversed safely if a migration fails?
**Answer**: Yes. Every codemod run produces a `.patch` file and a Reversal Manifest. In addition, `--worktree` execution isolates code edits in a disposable Git worktree, keeping the user's working branch completely untouched until approved.

### Q8: Is semantic validation actually testable without MS Excel installed?
**Answer**: Yes. Level 1 (Structural), Level 2 (OPC Relationship), and Level 3 (Semantic XML) run 100% in Node.js via `@berryn/xlsx-validate`. Level 4 (Consumer validation via headless LibreOffice) is optional and executes only when the binary is present.

### Q9: Is the ExcelJS compatibility facade sufficiently narrow to prevent false expectations?
**Answer**: Yes. The facade implements only the verified high-frequency subset (`readFile`, `writeFile`, `addRow`, primitive `getCell`). Calling any unevidenced API throws a loud `BerrynCompatibilityError` rather than silently doing nothing.

### Q10: Can CI operate without sending proprietary user artifacts to cloud services?
**Answer**: Yes. Berryn CLI commands (`berryn validate`, `berryn inspect`) run 100% offline (`--no-network`). CI workflows execute locally inside the runner without uploading workbook binaries anywhere.

### Q11: Is the report schema (`BERRYN_REPORT_V1`) stable enough for automated CI consumption?
**Answer**: Yes. The JSON schema enforces explicit versioning (`schemaVersion: "0.1.0"`). Additive fields preserve backwards compatibility, and diagnostic codes use branded strings.

### Q12: Is the test architecture sufficient to catch subtle OOXML regressions?
**Answer**: Yes. The test suite combines unit tests, integration tests, property-based tests (`fast-check`), stream fuzzing, security regression fixtures, and permissively licensed real-world workbooks.

### Q13: What is the biggest technical risk in the 0.1.0 umbrella scope?
**Answer**: Complex OOXML Relationship Graph Edge Cases. Excel files generated by third-party tools often contain non-standard relationship paths or malformed `[Content_Types].xml` overrides that could crash generic XML parsers if not strictly validated.

### Q14: What is the biggest product risk?
**Answer**: Developer hesitation to adopt a new CLI for dependency migrations. Mitigated by providing clear diff previews, zero-risk `--dry-run` modes, and evidence-backed Markdown summaries.

### Q15: What components can be implemented in parallel?
**Answer**: Once `@berryn/core`, `@berryn/diagnostics`, and `@berryn/security` are complete (Phase P0), `@berryn/project-inspect` (AST source parser) and `@berryn/xlsx-inspect` (ZIP/OPC parser) can be built in parallel.

### Q16: What components must be implemented strictly sequentially?
**Answer**: `@berryn/core` -> `@berryn/security` -> `@berryn/xlsx-inspect` -> `@berryn/xlsx-diff` / `@berryn/xlsx-validate` -> `@berryn/exceljs-compat` -> `berryn` CLI.

### Q17: What capabilities should NOT be built in 0.1.0?
**Answer**: 
1. Direct FFmpeg media processing logic.
2. Universal OOXML chart/pivot-table editing.
3. Hosted artifact cloud upload services.
4. Regex-based code search-and-replace tools.

### Q18: What failure vector could silently corrupt user workbook data?
**Answer**: Re-serializing `xl/styles.xml` or `xl/sharedStrings.xml` without preserving index mappings for unmodeled cell style elements. Prevented by strict index preservation tests and opaque part fallback.

### Q19: What could create false compatibility confidence?
**Answer**: Returning dummy fallback values or empty objects for unsupported ExcelJS methods. Mitigated by enforcing loud throwing errors on unevidenced method calls.

### Q20: What single failure condition would make the entire 0.1.0 release unsafe?
**Answer**: Shipping a vulnerability where a malicious `.xlsx` file containing a ZIP bomb or XXE payload bypasses `@berryn/security` guards and crashes or compromises the host runner.

## 3. Comprehensive Risk Register

| Risk ID | Risk Category | Risk Description | Probability | Impact | Mitigation Strategy | Failure Trigger / Indicator |
|---|---|---|---|---|---|---|
| **RSK-001** | Security | ZIP Bomb / Decompression Bomb vulnerability crashes CI runner or consumes disk space. | Medium | Critical | Streamed extraction with `maxEntryCount` (100,000), `maxTotalUncompressedBytes` (2 GB), and compression ratio guard (100:1). | Parser heap overflow or timeout on adversarial zip fixture. |
| **RSK-002** | Security | XXE attack via malicious `<!ENTITY>` payload in `sheet1.xml` exposes local host files. | Medium | Critical | Explicitly configure XML parsers to disable external entities, DTD processing, and XInclude (`resolveExternalEntities: false`). | Local file content detected in parsed XML output string during fuzzing. |
| **RSK-003** | Data Loss | Unmodeled OOXML parts (e.g. VBA macros, custom XML) stripped during workbook mutation. | High | High | Implement OPC Preservation Manifest. Opaque byte-for-byte retention of unmodeled parts. Reject mutation if preservation fails. | Output `.xlsx` missing `xl/vbaProject.bin` or emitting Excel repair prompt. |
| **RSK-004** | Compatibility | App crashes in production because ExcelJS facade mock returns `undefined` for unsupported API call. | Medium | High | Enforce Loud Failure Principle: throw `BerrynCompatibilityError` immediately with exact remediation steps. | Silent `TypeError` in downstream client code. |
| **RSK-005** | Reliability | Regex-based codemod rewrites incorrect code locations or breaks syntax. | High | High | Prohibit regex rewriting. Mandate `ts-morph` AST node transformations with TypeScript compiler validation. | Syntax error introduced in target client project after running `berryn migrate`. |
| **RSK-006** | Performance | Processing 100 MB compressed XLSX exceeds memory limits or takes > 30 seconds. | Medium | Medium | Use streaming XML parsers (`fast-xml-parser` stream mode) and memory budget checks in `@berryn/security`. | Heap allocation exceeding 512 MB during benchmark test suite. |
| **RSK-007** | Privacy | Proprietary workbook content or secrets exposed in CI logs or output reports. | Medium | High | Apply redaction filters in `@berryn/migration-report` to remove cell string values and local path strings. | Sensitive string payload found in stdout logs or report JSON. |
| **RSK-008** | Supply Chain | Compromised npm dependency injects malicious code during build or installation. | Low | High | Pin dependencies; use pnpm lockfiles; run SAST/SCA scanning; publish via GitHub Actions OIDC Trusted Publishing. | `pnpm audit` failure or unverified dependency version in lockfile. |
